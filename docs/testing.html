Testing Auth Switcher

Instructions for Chrome Web Store review · about two minutes

The extension has no account, no login and no server, so there are no credentials to hand over for it. It stores credentials for other sites.

To exercise it you need a site that issues an HTTP authentication challenge. httpbin.org provides one publicly, and the credentials it accepts are part of the URL — so two separate accounts can exist on the same host, which is exactly the situation this extension is built for. The response body names whichever account authenticated, so the result is directly visible rather than inferred.

Setup

  1. Install and pin the extension, then click its toolbar icon.
  2. Click the gear icon to open Settings.
  3. Under Site domains, type httpbin.org and press Enter. It appears as a chip.
  4. Click the gear again to leave Settings.

Add two accounts

  1. Click Add user — label Alice, username alice, password wonderland. Save.
  2. Click Add user again — label Bob, username bob, password builder. Save.

Verify the first account

  1. Make sure the popup shows Signed in as Alice; click Alice if not. Then open:
    https://httpbin.org/basic-auth/alice/wonderland Expected: the page loads with no Chrome credential prompt, and the body reads { "authenticated": true, "user": "alice" }

Verify switching — the core feature

  1. Open the popup and click Bob. The popup closes and the tab reloads.
  2. Open:
    https://httpbin.org/basic-auth/bob/builder Expected: loads with no prompt, body reads { "authenticated": true, "user": "bob" }
Why this matters: without the extension, Chrome caches Alice's credentials for httpbin.org in memory and reuses them until the browser is fully restarted. Closing the tab does not clear it, and neither does “Clear browsing data”. Bob would be unreachable in the same browsing session. That is the entire problem this extension solves.

Verify unrelated sessions survive a switch

  1. Sign in to any unrelated site where you hold a session.
  2. Switch users in the extension, then reload that unrelated site. Expected: you are still signed in there.
Why this matters for the <all_urls> permission: switching clears Chrome's HTTP auth cache, and the only API that does so (browsingData.remove) clears every cookie in the profile, globally, regardless of host permissions. The extension snapshots every cookie outside the configured domains and writes it back immediately afterwards. This step demonstrates that the broad host permission exists to restore the user's sessions, not to access those sites.

Optional — Digest authentication

  1. Add a user with username digestuser and password digestpass, select it, then open:
    https://httpbin.org/digest-auth/auth/digestuser/digestpass Expected: authenticates with no prompt. Digest is handled by the same listener.

Optional — private window isolation

  1. Enable Allow in Incognito at chrome://extensions → Details.
  2. Open a private window, open the popup there, and switch to a different user than the one selected in your normal window. Expected: each window keeps its own signed-in user, independently.
One deliberate behaviour that can look like a bug: the extension refuses to send Basic credentials over plain http:// to a public host, because Basic is reversible base64 rather than encryption. Intranet addresses (loopback, RFC1918 ranges, single-label names, .local) are exempt, since http-only internal tools are the use case. Every URL above is https, so this never fires during the test.
No credentials, cookies or browsing data are transmitted anywhere. The extension makes no network requests of its own and contacts no server. See the privacy policy or the source.
